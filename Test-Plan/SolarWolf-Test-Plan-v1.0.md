## 1. 测试目标

在范围受控的前提下，对 SolarWolf 的核心玩家交互、碰撞与生命状态、特殊道具与计时器、UI/HUD 与存档进行系统测试。项目重点是形成可复查的测试设计、真实执行记录、可复现的缺陷证据，以及针对确认缺陷的 Python 源码分析和少量有意义的自动化测试。

## 2. 测试范围

### 2.1 范围内模块

| 模块 | 测试重点 |
| --- | --- |
| 玩家移动与小方块交互 | 方向键移动、游戏区域边界、绿色与黄色小方块的有效接触、关卡完成。 |
| 危险物、死亡与生命状态 | 火球、刺球、死亡、固定复活点、火球清除、生命跨关保留、生命耗尽返回主界面。 |
| 特殊道具与计时器 | 时钟、清屏道具、护盾、道具跨屏幕边界、计时器显示与提前完成关卡的跳关效果。 |
| UI / HUD 与存档 | 右侧状态栏、焦点切换后的暂停提示、BUG-UI-001、存档选择、存档独立性和 `Lives Used` 显示。 |

### 2.2 范围外内容

- 对 SolarWolf 全部关卡、全部美术资源、音效与所有隐藏机制进行完整覆盖。
- 以 GitHub Issues 中的已知问题作为第一轮测试输入。
- 为了增加作品集数量而人为制造缺陷、伪造测试结果或编造证据。
- 对 GUI 进行大规模、脆弱的自动化点击测试。
- 修改或修复 SolarWolf 源码；源码仅用于后续缺陷分析和可测试逻辑的理解。

## 4. 测试方法

| 方法 | 使用方式 |
| --- | --- |
| 功能测试 | 验证玩家操作、收集、危险物、道具、生命和存档的可观察行为。 |
| 探索性测试 | 已完成第一轮多局黑盒游玩；后续仅用于补充新发现或验证异常。 |
| 等价类划分与边界值分析 | 对绿色/黄色小方块、生命数量、计时器、屏幕边界等适合控制的输入与状态设计测试。 |
| 状态转换测试 | 验证开始、游玩、暂停、死亡、复活、过关、生命耗尽返回主界面等状态及显示同步性。 |
| 负向测试 | 仅测试真实玩家可合理触发的异常操作或状态，不强制制造难以稳定重复的帧级操作。 |
| UI / 可用性测试 | 验证 HUD、暂停提示、存档选择和焦点切换后的界面恢复。 |
| 回归测试 | BUG-UI-001 在后续源码分析或环境变化后，使用同一复现路径复测。 |
| 白盒分析与 pytest | 仅在黑盒证据已建立后，对确认缺陷或稳定逻辑阅读 Python 源码并选择性自动化。 |

## 5. 测试策略与执行顺序

1. 根据本计划为四个范围内模块编写测试场景和正式 Test Cases。
2. 执行每个用例，并记录实际结果、状态、备注和所关联的 Evidence 文件。
3. 出现异常时，先独立复现并收集证据；只有确认与预期不符且可说明影响时，才创建正式 Bug Report。
4. 对已确认的 BUG-UI-001 阅读相关 Python 源码，记录可能相关的模块与证据边界；未验证前不宣称已确定根因。
5. 选择不依赖 GUI、行为稳定的逻辑，以 pytest 编写少量自动化测试。
6. 对确认缺陷与核心流程执行回归测试，并汇总为 Test Report。

## 6. 已知测试基线

首次黑盒探索已记录基础用户流程。其后通过多局实际游玩，对核心规则开展了主动黑盒验证，并确认 BUG-UI-001：切回游戏窗口后，右侧状态栏可能未完整重绘。该缺陷有两张直接异常截图；存档选择、正常游戏和首次切屏返回的暂停界面均归类为游戏记录，其中暂停界面作为缺陷复现上下文被引用。详情见[主动黑盒测试记录](Active-Black-Box-Test-Record-01.md)。

此基线用于设计用例，不替代正式测试用例的执行结果。

## 7. 缺陷与证据管理

- 缺陷编号格式：`BUG-<模块>-<三位序号>`，例如 `BUG-UI-001`。
- 每份正式 Bug Report 应包含：环境、前提条件、复现步骤、预期结果、实际结果、严重性、优先级、可复现性、影响说明和 Evidence。
- 图片证据存放于 `Evidence/`，文件名使用缺陷编号与场景描述。
- 不能复现、证据不足或预期行为不明确的问题，先记录为 Observation，不升级为正式缺陷。

## 8. 进入与完成标准

### 进入标准

- 游戏能够在记录的测试环境中启动。
- 已完成第一轮黑盒探索并记录核心可观察行为。
- 已确定四个范围内模块。

### 完成标准

- 四个范围内模块均有正式 Test Cases 和真实执行记录。
- 已确认缺陷均有可复现步骤和证据；未确认问题不被包装为缺陷。
- 已完成 BUG-UI-001 的白盒分析记录，且结论与证据范围一致。
- 已实现并执行少量针对稳定逻辑的 pytest 自动化测试。
- 已完成核心流程与确认缺陷的回归测试，并产出最终 Test Report 和项目 README。

## 9. 风险与应对

| 风险 | 应对措施 |
| --- | --- |
| 部分道具或状态出现频率低 | 记录“未观察到”，不将其误记为失败；后续结合源码和可控逻辑测试补充。 |
| 精确帧级边界难以手工复现 | 不作为黑盒主测试项，转入后续白盒分析或 pytest 自动化。 |
| 全屏窗口不便截图 | 使用屏幕拍摄照片；照片前后对照并保留文件名与复现上下文。 |
| 已知 UI 缺陷影响观察 | 将 BUG-UI-001 单独记录，必要时重启游戏后继续其他模块测试。 |
| 被测游戏与个人成果混淆 | 在 README、测试计划和报告中持续标明 SolarWolf 的原作者与“被测游戏”身份。 |
